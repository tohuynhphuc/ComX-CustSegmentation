\chapter{Data Warehouse Design}
\label{chap:warehouse}

The CompanyX data warehouse employs a \textbf{fact constellation (galaxy) schema} centered on customer analytics. Rather than modeling transactional order lines, the warehouse establishes the \emph{individual customer} as the core analytical grain. Two complementary fact tables share standardized dimensions for customer demographics, socioeconomic profiles, machine learning model versions, and calendar dates, as illustrated in Figure~\ref{fig:DWH_design}.

\section{Staging Layer}
\label{subsec:stg_tab}
The staging table \texttt{stg.CustomerProfile} serves as a temporary landing zone during ETL extraction. It uses a composite primary key consisting of a unique batch identifier (\texttt{BatchID}) and the source customer key (\texttt{CustomerKey}). Each execution of the SSIS customer package generates a new GUID for \texttt{BatchID}, truncates prior staged records, extracts changed demographic rows from the source database, and executes the merge procedure \texttt{usp\_ApplyCustomerProfileBatch}. This batch-scoped staging design ensures atomic transactions and prevents partial data loads from corrupting dimension tables.

\section{Dimension Layer and Slowly Changing Dimensions}
\subsection{DimCustomerProfiling (SCD Type 0 and Type 1)}
\texttt{DimCustomerProfiling} maintains one current demographic record per customer, keyed by \texttt{CustomerKey\_Str} (converted from the source \texttt{CustomerID}). Attributes in this dimension are managed under two SCD strategies:
\begin{itemize}
    \item \textbf{SCD Type 0 (Fixed):} Attributes such as \texttt{BirthDate} are immutable once inserted and never modified.
    \item \textbf{SCD Type 1 (Overwrite):} Personal attributes that change over time---including \texttt{Gender}, \texttt{MaritalStatus}, \texttt{TotalChildren}, \texttt{HomeOwnerFlag}, and \texttt{NumberCarsOwned}---are updated directly in place. This provides instant access to current customer statuses without multiplying dimension rows.
\end{itemize}

\subsection{DimClusterProfiling (SCD Type 2)}
\texttt{DimClusterProfiling} stores evolving socioeconomic and regional characteristics, including yearly income, education level, occupation, country, and region group.

To preserve historical context, these attributes are tracked using \textbf{SCD Type 2}:
\begin{itemize}
    \item When a demographic change is detected, the existing active row is closed by setting its \texttt{EffectiveEndDate} to the current date and \texttt{IsCurrent = 0}.
    \item A new record is inserted with a unique surrogate key (\texttt{ClusterProfilingSK}), effective date intervals, and \texttt{IsCurrent = 1}.
\end{itemize}
This mechanism enables historical RFM snapshots to be accurately linked with the exact socioeconomic profile the customer possessed at that point in time.

\subsection{DimModelConfig (ML Model Versioning)}
\texttt{DimModelConfig} operationalizes machine learning by persisting trained K-Means configurations directly in the relational database. For each model version, five rows are stored (one per cluster), recording:
\begin{itemize}
    \item Cluster ID (0 to 4) and human-interpretable business segment name;
    \item Feature scaling parameters (mean and standard deviation for Recency, Frequency, and Monetary);
    \item Centroid coordinates in standardized 3D feature space;
    \item Validity dates (\texttt{StartDate}, \texttt{EndDate}) and an active status flag (\texttt{IsActive}).
\end{itemize}
Persisting centroids and scaler parameters allows downstream scoring scripts to assign incoming customers to clusters instantly using matrix multiplication, eliminating the need to re-fit K-Means on every transaction.

\subsection{DimDate}
\texttt{DimDate} provides a standard enterprise calendar dimension with attributes including calendar year, quarter, month, day, and day of week. The initialization script pre-populates dates from \textbf{1 January 2010} through twenty years beyond execution, comfortably covering the source transaction history (2011--2014) and future operational reporting horizons.

\section{Fact Layer}
\subsection{FactCustomerSnapshot (Monthly Periodic Snapshot)}
\texttt{FactCustomerSnapshot} captures the behavioral state of every active customer at standardized monthly intervals. Its analytical grain is \emph{one customer at one calendar month-end date}, uniquely identified by \texttt{CustomerKey\_Str} and \texttt{SnapshotDateKey}.

At each month-end, the snapshot procedure reconstructs customer metrics from raw transactions:
\begin{itemize}
    \item \texttt{Frequency365d}: Distinct sales orders placed within the trailing 365 days;
    \item \texttt{Monetary365d}: Total order line revenue within the trailing 365 days;
    \item \texttt{RecencyDays}: Elapsed days since the customer's most recent purchase (can exceed 365 days).
\end{itemize}
Scheduled to run at 00:05 on the first day of each month, this table provides the foundation for longitudinal trend analysis, customer churn tracking, and annual model retraining.

\subsection{FactCustomerRFMLive (Purchase-Triggered Operational Fact)}
\label{subsec:factcustomerRFMlive}
\texttt{FactCustomerRFMLive} delivers near-real-time operational intelligence. Instead of logging every order line, it maintains exactly one row per customer reflecting their state immediately after their latest transaction.

When new sales are committed in the source database, the ETL process recalculates the affected customer's trailing 365-day frequency and monetary spend, while setting purchase-time recency to zero. The Python scoring script then maps the standardized vector against \texttt{DimModelConfig} to update the customer's cluster assignment. 

By separating purchase-event operational scoring (\texttt{FactCustomerRFMLive}) from periodic historical observation (\texttt{FactCustomerSnapshot}), the warehouse achieves both high-frequency operational responsiveness and comprehensive retrospective reporting without unnecessary computational overhead.
