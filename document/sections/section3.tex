\chapter{Data Warehouse Design}
\label{chap:warehouse}

The proposed warehouse follows a \textbf{fact constellation (galaxy) schema}: two customer-centred fact tables share dimensions for customer profiles, historical demographic versions, model configuration, and calendar dates. The diagram in Figure~\ref{fig:DWH_design} is the team's final warehouse design. A separate general-purpose sales fact is intentionally excluded because the project's analytical grain is the \emph{customer}, not the sales line. The RFM procedures read the required transactions from the source \texttt{CompanyX} database.

\section{Staging Layer}
\label{subsec:stg_tab}
The customer staging table uses a composite primary key combining the batch ID and customer key. It receives the demographic records selected by SSIS before they are merged into the two profile dimensions. A new batch identifier distinguishes the records associated with a particular ETL run. The active package clears the staging table at the beginning of a run and passes the batch identifier to \texttt{usp\_ApplyCustomerProfileBatch}.

This is a \emph{relational staging area}, not a durable message queue or an archive of every ETL batch. Its batch identifier makes processing scoped and repeatable; transactional error handling in the merge procedure protects the consistency of the dimension changes. Keeping a long-term execution log or recovering an interrupted run from retained staging records would require additional mechanisms.

\section{Dimension Layer and Slowly Changing Dimensions}
\subsection{DimCustomerProfiling}
This dimension stores one current demographic row per customer. The source \texttt{CustomerID} field in \texttt{Sales.Customer} is converted to an \texttt{NVARCHAR(20)} value, \texttt{CustomerKey\_Str}, which is reused as the primary key and in the related fact tables. Birth date is handled as an \textbf{SCD Type 0} attribute: once populated, the original value is retained. Gender, marital status, number of children, home ownership, and number of cars are handled as \textbf{SCD Type 1} attributes: detected changes overwrite the current value instead of preserving previous versions. This design retains straightforward access to current customer information without unnecessarily multiplying records.

\subsection{DimClusterProfiling}
\texttt{DimClusterProfiling} stores socioeconomic and geographical characteristics including yearly income, education, occupation, country, and region. These are managed as \textbf{SCD Type 2} attributes. A changed profile closes the preceding version and inserts a new row with a distinct \texttt{ClusterProfilingSK}, effective dates, and an \texttt{IsCurrent} flag. This allows analysts to inspect demographic versions captured by the warehouse and associate customer RFM observations with the available historical profiles.

An important distinction is that this dimension's name refers to \emph{customer profiling}, not the five K-Means segment definitions. It also cannot recover demographic history from before the first successful warehouse load; retrospective sales snapshots should not be interpreted as proof of what those demographic fields were in earlier years.

\subsection{DimModelConfig}
\texttt{DimModelConfig} persists the output of K-Means training. Each model version contains five rows, one for each cluster, with its numeric cluster ID, assigned business segment name, per-feature scaling means and standard deviations, and centroid coordinates in standardized feature space. \texttt{StartDate}, \texttt{EndDate}, and \texttt{IsActive} distinguish model versions over time. This resembles Type 2 effective-dated version management, but it represents \emph{retrained models}, not changing customer demographics. Persisting the parameters lets the Python live scorer reuse a trained model without refitting K-Means for every customer.

\subsection{DimDate}
Each row of \texttt{DimDate} corresponds to a calendar date and exposes fields such as year, quarter, day, and month. The schema initialization script fills missing dates from \textbf{1 January 2010} through the date of execution plus twenty calendar years. The range covers the source sales period and the intended future reporting horizon; rerunning the script may extend it as needed.

\section{Fact Layer}
\subsection{FactCustomerSnapshot}
\texttt{FactCustomerSnapshot} is a \textbf{monthly periodic snapshot fact}. Its analytical grain is \emph{one eligible customer at one month-end date}, uniquely identified by customer and \texttt{SnapshotDateKey}. The snapshot procedure reconstructs RFM from sales transactions as of that date. \texttt{Frequency365d} counts distinct purchases and \texttt{Monetary365d} sums sales order-line values within the trailing 365 days. \texttt{RecencyDays} measures the number of days since the latest purchase and can exceed 365 days. The fact also stores model references, a segment label, scaled features, and the associated customer profile key where available.

Snapshots are calculated independently from the transaction-triggered live table; therefore, their row counts do \emph{not} necessarily match the live table. The monthly process is scheduled at 00:05 on the first day of the following month and uses the preceding calendar month-end as the snapshot date. This separates the historical \emph{as-of-date} view from purchase-event scoring and makes it possible to observe inactivity even when a customer places no new order.

\subsection{FactCustomerRFMLive}
\label{subsec:factcustomerRFMlive}
\texttt{FactCustomerRFMLive} maintains one record per customer rather than one record per order. When relevant sales changes are detected, the system recalculates the affected customer's orders and inserts or updates that record. The analysis date is intentionally set to the \emph{customer's latest purchase date}; consequently, the purchase-time \texttt{RecencyDays} is zero. Frequency and monetary value summarize the 365 days ending on that purchase date. Python then assigns a segment using the latest active configuration in \texttt{DimModelConfig}.

This is a \textbf{purchase-triggered operational view}, not a table that continuously ages every inactive customer. Refreshing all customers after every transaction would be unnecessarily expensive for the team's intended near-real-time workflow. Month-end snapshots supply the complementary time-based view used for inactivity trends and historical comparison. Throughout the report, the word \emph{live} refers to this operational purchase-time state; it should not be confused with the dashboard's final historical snapshot dated 30 June 2014.
