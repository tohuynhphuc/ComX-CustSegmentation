\section{The General View}
Figure~\ref{fig:system_workflow} summarizes the two complementary data paths and annual model training. The customer-demographics load and purchase-triggered RFM path support operational decisions; the monthly snapshot path preserves the state of customers at a common evaluation date.

\begin{figure}[htbp]
    \centering % Căn giữa hình ảnh
    \includegraphics[width=0.8\textwidth]{finalSystemWorkflow.png}
    \caption{High-level flow from CompanyX transactions to RFM facts, model configurations, and reporting.}
    \label{fig:system_workflow} % Nhãn để dùng cho lệnh tham chiếu \ref{}
\end{figure}

The first path begins with a customer transaction. The deployed one-minute SSIS jobs load changed customer profiles and refresh RFM for affected customers in \textbf{FactCustomerRFMLive}. The Python scorer then applies the latest active configuration from \texttt{DimModelConfig}. It log-transforms and standardizes the purchase-time RFM features, computes distances to stored centroids, and writes back the segment and model key. Because this view is evaluated on the most recent purchase date, a refreshed customer's recency is zero by design; customers are not rescored simply because a day passes.

The second path is scheduled for 00:05 on the first day of each month. It computes RFM as of the \emph{previous month-end} directly from source transactions and appends the result to \textbf{FactCustomerSnapshot}. The historical snapshot scoring procedure uses stored model definitions. These snapshots are also the training source for new annual K-Means versions: training takes the year-end snapshot and writes scaler statistics, centroids, and segment mappings into \texttt{DimModelConfig} for subsequent scoring.

For the historical initial load, the team used \texttt{bootstrap.py} to create the first 2011 model and retrospectively label early snapshots once that model was available. Subsequent models were trained on the 2012 and 2013 year-end snapshots using \texttt{train\_model.py}; no 2014 model was trained because source transactions end on 30 June 2014. This historical reconstruction must be distinguished from predictions genuinely available in those earlier months. The Power BI view discussed in Chapter~\ref{chap:power_bi} takes the 30 June 2014 historical snapshot as its final reference state.

\section{ETL Pipeline \& Data Flow}
This section follows the three SSIS packages supplied in the project: \texttt{Package\_Customer\_}\linebreak[1]\texttt{Incremental.dtsx}, \texttt{RFM\_Live.dtsx}, and \texttt{RFM\_Snapshot.dtsx}. The following screenshots and SQL excerpts are from the team's implementation; full routine definitions are included in the system resources. The customer and live packages have been deployed on a one-minute schedule, while the snapshot package is scheduled monthly.

    \label{fig:data_flow_cust} % Nhãn để dùng cho lệnh tham chiếu \ref{}

Overall, there are three components:
\begin{itemize}
    \item[\textbf{vPersonDemographics:}] the OLE DB Source extracts changed demographic records from the CompanyX operational database:
    \begin{lstlisting}[caption={Table Selection}, label={lst:tab_select}]
SELECT
    c.CustomerID AS CustomerKey,
    d.BusinessEntityID,
    CAST(d.BirthDate AS DATE) AS BirthDate,
    d.Gender,
    d.MaritalStatus,
    d.YearlyIncome,
    d.TotalChildren,
    d.Education,
    d.Occupation,
    CAST(d.HomeOwnerFlag AS TINYINT) AS HomeOwnerFlag,
    d.NumberCarsOwned,
    CAST(d.DateFirstPurchase AS DATE) AS DateFirstPurchase,
    st.[Name] AS CountryName,
    st.[Group] AS RegionGroup
FROM Sales.vPersonDemographics AS d
INNER JOIN Sales.Customer AS c
    ON d.BusinessEntityID = c.PersonID
LEFT JOIN Sales.SalesTerritory AS st
    ON c.TerritoryID = st.TerritoryID
LEFT JOIN CompanyX_DataWarehouse.dbo.DimCustomerProfiling AS dc
    ON dc.CustomerKey_Str = CONVERT(NVARCHAR(20), c.CustomerID)
LEFT JOIN CompanyX_DataWarehouse.dbo.DimClusterProfiling AS dp
    ON dp.CustomerKey_Str = CONVERT(NVARCHAR(20), c.CustomerID)
   AND dp.IsCurrent = 1
WHERE d.DateFirstPurchase IS NOT NULL
  AND (
       dc.CustomerKey_Str IS NULL
       OR dp.CustomerKey_Str IS NULL
       OR EXISTS (
           SELECT d.Gender, d.MaritalStatus, d.TotalChildren,
                  CONVERT(BIT, d.HomeOwnerFlag), d.NumberCarsOwned
           EXCEPT
           SELECT dc.Gender, dc.MaritalStatus, dc.TotalChildren,
                  dc.HomeOwnerFlag, dc.NumberCarsOwned
       )
       OR EXISTS (
           SELECT d.YearlyIncome, d.Education, d.Occupation,
                  st.[Name], st.[Group]
           EXCEPT
           SELECT dp.YearlyIncome, dp.Education, dp.Occupation,
                  dp.CountryName, dp.RegionGroup
       )
  );
    \end{lstlisting}
    The extraction selects customers with a first purchase whose relevant demographic attributes are missing or different from the warehouse's current values. The \texttt{EXCEPT} predicates compare groups of attributes, including nullable values, without requiring a complete reload on every execution. This is a \emph{change-detection} form of incremental loading rather than a source timestamp watermark.

    \item[\textbf{Derived Column:}] normalizes input values and handles missing demographic attributes before loading into staging.
    \begin{figure}[htbp]
    \centering % Căn giữa hình ảnh
    \includegraphics[width=0.8\textwidth]{DerivedColumn.png}
    \caption{Derived Column: input data cleaning step.}
    \label{fig:derived_col} % Nhãn để dùng cho lệnh tham chiếu \ref{}
\end{figure}
    The configured fallback values include ``Unknown, 0, and ``U for selected attributes; these are data-cleaning conventions, not evidence that the original source value is known.
    \item[\textbf{stg Customer Profile:}] the destination writes the transformed rows into the staging table described in Section~\ref{subsec:stg_tab}, ready for the T-SQL merge.
\end{itemize}

Finally, the \emph{Apply Customer Merge} SQL task executes the batch procedure if rows were staged. That procedure applies Type 0/1 customer rules and Type 2 demographic history in a transaction:
\begin{lstlisting}[caption={Merge}, label={lst:merge}]
DECLARE @BatchID UNIQUEIDENTIFIER = CONVERT(UNIQUEIDENTIFIER, ?);
IF EXISTS (
    SELECT 1
    FROM stg.CustomerProfile
    WHERE BatchID = @BatchID
)
BEGIN
    EXEC dbo.usp_ApplyCustomerProfileBatch @BatchID = @BatchID;
END;
\end{lstlisting}

    \caption{FactCustomerRFMLive handling.}

The first SSIS task, \emph{Refresh Customer RFM Live}, calls \texttt{usp\_RefreshCustomerRFMLive}. A stored watermark tracks the last processed source modification timestamp. Changes to sales headers or order details identify the affected customers; their full order history is aggregated once, using the customer's latest purchase date as the analysis date. The result is merged into \texttt{FactCustomerRFMLive} (insert for a new customer, update for a previously loaded customer).

The second, enabled task is \emph{Score Live Customers}; its Python script is \texttt{live\_clustering.py}. It loads the \emph{latest active} model version, applies saved scaling parameters and centroids, and updates customers whose model key or segment has changed. An older SQL live-clustering task remains in the repository but is disabled in the deployed package and is not the operational scoring path. The approximately one-minute job interval makes this a \emph{near-real-time batch} process rather than event-by-event synchronous processing.

The first task, \emph{Append Monthly Customer Snapshot}, determines the previous month-end and calculates historical RFM values for the \textbf{FactCustomerSnapshot}:
\begin{lstlisting}[caption={Monthly RFM Calculation}, label={lst:month_RFM}]
DECLARE @SnapshotDate DATE;

SET @SnapshotDate = EOMONTH(GETDATE(), -1);

EXEC dbo.usp_AppendMonthlyRFMSnapshot
    @SnapshotDate = @SnapshotDate;
\end{lstlisting}

The subsequent \emph{Cluster Snapshot} task assigns segment labels using the available effective-dated model definitions:
\begin{lstlisting}[caption={Monthly Cluster Segment}, label={lst:month_cluster}]
EXEC dbo.usp_ClusterCustomerRFMSnapshot;
\end{lstlisting}





\section{Annual Model Training and Scheduling}
The training scripts use the final snapshot of a year as their input. The first model was established by \texttt{bootstrap.py} using the 2011 year-end data, with historical 2011 snapshots labeled retrospectively. The next training runs were executed for 2012 and 2013; each saved model version has five cluster rows and a validity start date in \texttt{DimModelConfig}. The active live scorer uses the most recently active model, while the historical snapshot procedure selects effective-dated model configurations and includes bootstrap handling for the earliest periods.

The project includes the Airflow DAG \texttt{rfm\_year\_end\_training}, which specifies a yearly run on 1 January. At the time of submission, the DAG's unattended end-to-end execution had not been verified. In particular, its configured start time (00:00) precedes the monthly SSIS snapshot schedule (00:05); a production-ready dependency would require waiting for the December snapshot to be committed before training begins. The DAG also needs an environment-independent Python module path on the deployment machine. These do not prevent the separately executed annual training workflow from being demonstrated, but remain operational integration tasks.

\section{Pipeline Outputs}
Successful runs produce one current Type 1 customer profile per customer, effective-dated Type 2 demographic records, a purchase-triggered RFM record for affected customers, periodic monthly customer snapshots, and a persisted set of cluster parameters. The Power BI dashboard reads the warehouse's historical June 2014 analytical view. This separation allows both immediate post-purchase decisions and longer-term segment comparisons without requiring an update of every live customer after each purchase.
